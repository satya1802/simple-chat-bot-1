|---|---|---|
| backend | FastAPI | The backend's main job is to sit between the browser and the hosted LLM: forward the conversation, stream the reply back as it's generated, and enforce per-IP rate limiting. | cloud | AWS | You need somewhere reliable to run a web app and backend at modest scale with low ongoing cost, and the ability to scale up if the free, open-to-anyone chatbot gets popular. AWS covers all of this and keeps your options open as usage grows. |
| database | PostgreSQL | This product deliberately keeps chat history only in the user's browser with no accounts, so it needs very little persistent storage. PostgreSQL is the dependable default for the small amount you will keep server-side — for example rate-limit records or basic usage/abuse logging — and leaves room to add saved history later if you ever introduce accounts. |
| frontend | React | Your product is a responsive, ChatGPT-style chat screen that has to work well on both desktop and mobile browsers, with messages streaming in live and history held in the browser for the current session. React handles exactly this kind of single-screen, interactive UI, and keeping the conversation in the browser's own session storage (no accounts) is straightforward with it. |

## EPIC-002: AI Conversation

The core open-ended, ChatGPT-style text conversation with the AI assistant. The assistant maintains context within a single conversation and streams its responses into the chat UI. Responses are plain text only.

Assumptions surfaced: responses are generated by a hosted large language model — per the chosen delivery scope the provider is Anthropic Claude and requires an ANTHROPIC_API_KEY. NOTE: this conflicts with the earlier confirmed assumption that named OpenAI (OPENAI_API_KEY) as the default provider; the delivery scope's choice of Anthropic Claude has been drafted here. Out of scope for this version: file/document/image uploads, live web search, and configurable persona.

### US-004: Send a message and receive an AI response

**Priority:** critical

> As a user, I want to type a text message and receive a reply from the AI assistant, so that I can have an open-ended conversation and get answers.

| ID | Given | When | Then |
|---|---|---|---|
| AC-006 | the chat interface is open | the user types a text message and submits it | the message appears in the conversation and the assistant generates a plain-text reply that is displayed in the chat |
| AC-007 | a user has submitted a message | the hosted LLM (Anthropic Claude) returns a response | the assistant's reply is shown as a distinct message attributed to the assistant |
| AC-008 | the ANTHROPIC_API_KEY is missing or the LLM call fails | a user submits a message | the user is shown a clear error message and the interface remains usable to retry |

### US-005: See AI responses stream in as they are generated

**Priority:** high

| AC-010 | a response is streaming | the generation completes | the message is shown as complete and the input is ready for the next message |

### US-006: Assistant remembers earlier messages in the same conversation

**Priority:** high

## EPIC-003: Session Management & History

Chat history is kept only within the current browser session and is not saved server-side or across devices, since there are no accounts. Users can start a new conversation / clear the current session.

Assumptions surfaced: chat history persists only within the current browser session (e.g. local/session storage); there is no cross-device or server-side per-user saved history.

### US-007: Keep chat history within the current browser session

**Priority:** high

> As a user, I want my conversation to remain visible while I stay in the same browser session, so that I can scroll back and review the exchange during my session.

| ID | Given | When | Then |
|---|---|---|---|
| AC-013 | a user has had an exchange in the current session | they continue using the application within the same browser session | the previous messages of that conversation remain visible and scrollable |
| AC-014 | a user's conversation exists only in the current browser session | the browser session ends or the session storage is cleared | the conversation is no longer retained and no server-side per-user copy is kept |

### US-008: Start a new conversation / clear the current session

**Priority:** medium

| ID | Given | When | Then |
|---|---|---|---|

| AC-016 | the user has started a new conversation | they send the next message | the assistant does not use the cleared conversation's earlier messages as context |

## EPIC-004: Abuse Protection & Cost Control

Because access is open with no login and the assistant calls a paid hosted LLM, basic rate limiting / abuse protection is applied to control cost and misuse.

Assumptions surfaced: basic per-IP rate limiting/abuse protection is applied; expected scale is modest (small-to-moderate concurrent users) with no fixed deadline.

### US-009: Limit request rate to control cost and misuse

**Priority:** high

> As a product operator, I want basic per-IP rate limiting applied to chat requests, so that I can control LLM costs and reduce abuse while access remains open.

| ID | Given | When | Then |
|---|---|---|---|
| AC-017 | an anonymous visitor is sending messages | their request rate from a single IP exceeds the configured limit | further requests are throttled and the user is shown a clear message that they are sending requests too quickly |
| AC-018 | a visitor has been rate limited | they wait and their rate falls back within the allowed limit | they are able to send messages again normally |
